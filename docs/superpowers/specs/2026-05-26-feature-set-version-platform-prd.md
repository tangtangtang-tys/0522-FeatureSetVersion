# 机型功能集字典与版本记录平台产品需求文档（PRD）

## 1. 文档概述

### 1.1 文档名称

机型功能集字典与版本记录平台产品需求文档（PRD）

### 1.2 文档目的

本文件用于统一机型功能集字典与版本记录平台的产品背景、目标、范围、流程、功能需求、非功能需求与阶段规划，作为产品、研发、测试、交付等角色的共识基础。

### 1.3 文档定位

本 PRD 采用“可评审 + 可汇报”的平衡型写法：

- 对内可作为产品、研发、测试的需求评审依据
- 对上可作为立项、规划、阶段汇报的结构化材料
- 对后续迭代可作为平台分阶段建设的需求基线

### 1.4 适用范围

本文件覆盖：

- 当前 MVP 功能集字典模块
- 一期机型功能集字典与版本记录平台建设范围
- 平台长期规划方向与分阶段路线图

---

## 2. 背景概述与问题定义

### 2.1 业务背景

当前摄像机 IoT 产品线在功能能力定义、版本沉淀、机型差异管理和对外承诺上，仍存在大量依赖研发字段、Excel、历史文档与人员经验的情况。虽然现有系统已经具备功能项维护、版本入口、导入能力等基础能力，但整体仍偏研发工具视角，尚未形成跨产品、研发、测试、销售、交付、售后可共同使用的能力治理平台。

在机型管理场景中，一个功能能力往往同时影响：

- 机型定位与产品分层
- 硬件选型与 BOM 组合
- 固件、App、云平台、算法实现边界
- 测试范围与验收策略
- 销售承诺与交付说明
- 售后定位与升级判断

因此，需要将现有零散的“功能项维护能力”升级为“机型功能集字典与版本记录平台”，使其成为产品能力事实源和版本治理中心。

### 2.2 当前问题

当前阶段主要存在以下问题：

1. 功能项已被维护，但产品承诺视角不足，难以形成完整可售卖、可交付的能力包。
2. 功能项可以演进，但缺少功能集整体版本基线，无法清晰回答“某机型某版本到底具备哪些能力”。
3. 数据维护动作已存在，但缺少从需求引入到版本沉淀、日志追溯的完整流程闭环。
4. 角色协同不足，产品、研发、测试、售前、售后关注点尚未统一到同一平台事实源。
5. 历史定义与版本追溯关系弱，删除、变更、下线等动作风险较高。
6. 当前字段结构偏自然语言表达，长期难以支撑自动化测试、版本映射、依赖分析和数据复用。

### 2.3 核心问题定义

平台需要解决的核心问题是：

如何建立一个可规划、可维护、可沉淀、可追溯的机型能力治理平台，使摄像机产品线能够围绕“功能集”和“功能集版本”形成统一的产品定义语言，并支撑多角色协同与分阶段扩展。

## 3. 产品目标与成功指标

### 3.1 产品目标

#### 目标一：建立能力定义的统一事实源

将功能项、功能集、功能集版本从分散字段、临时表格和人员经验中抽离出来，形成结构化、可维护的能力资产。

#### 目标二：建立版本治理与能力追溯机制

通过功能集版本，固化某一时间点对外可承诺、对内可交付的能力快照，避免多版本、多机型、多部门之间的口径偏差。

#### 目标三：建立跨角色协同的最小治理闭环

围绕需求引入、功能定义、功能集编排、版本沉淀与日志追溯，先完成最小闭环，再逐步扩展到机型绑定、软件版本映射、测试验收和审批体系。

### 3.2 成功指标

#### MVP 阶段

- 100% 的新建功能集通过平台录入，不再通过离散文档维护
- 100% 的功能集版本形成平台内版本记录
- 查询某功能集与其版本记录的平均操作路径不超过 3 步
- 支持基于名称、编码检索功能集，查询结果可正确联动详情页
- 关键版本操作（创建、保存、编辑、删除）100% 保留日志记录

#### 一期阶段

- 80% 以上的标准机型能力定义通过功能集版本进行管理
- 60% 以上的跨角色问题确认可直接通过平台完成初步判断
- 销售、测试、交付口径不一致导致的人工确认次数明显下降

#### 长期阶段

- 平台成为机型能力定义、版本映射与能力追溯的统一事实源
- 能力查询、版本对比、机型绑定、测试范围生成形成完整链路

## 4. 需求范围与非目标

### 4.1 当前 MVP 范围

当前 MVP 聚焦 `功能集字典` 模块，包含以下范围：

- 功能集列表展示
- 按功能集名称、功能集编码查询
- 新增、编辑、启停功能集
- 功能集详情查看
- 功能集版本记录维护
- 版本列表与操作日志查看
- 新增、查看、编辑、删除版本记录
- 批量导入功能集及版本
- 字段规范说明
- 流程与交互说明页

### 4.2 一期范围

在 MVP 基础上，一期建议补齐以下能力：

- 功能项字典结构化管理
- 功能集与功能项关系编排
- 功能集版本评审与状态治理（待评审、已冻结、已废弃等）
- 审批与评审记录
- 引用关系校验
- 历史版本对比
- 删除/归档机制与日志审计

### 4.3 长期平台范围

长期平台建议逐步扩展以下模块：

- 机型功能集绑定
- 软件版本映射
- 测试与验收
- 多机型对比、多版本对比
- 多角色权限体系
- 项目定制转标准能力治理

### 4.4 非目标

本轮 PRD 明确不要求在当前 MVP 内完成以下内容：

- 完整的机型、SKU、区域、项目绑定页
- 固件、App、云平台版本映射页
- 自动生成测试用例或自动化测试平台
- 全量审批流引擎
- 大屏驾驶舱式统计分析页面
- 全平台 BI 或经营分析模块

## 5. 用户角色与典型场景

### 5.1 核心用户角色

#### 产品经理

关注能力边界、版本规划、对外承诺和阶段节奏。

#### 研发人员

关注字段定义、实现边界、兼容性、版本依赖和历史追溯。

#### 测试人员

关注版本范围、验收基线和变更影响。

#### 销售/售前

关注机型卖点、能力差异和可承诺范围。

#### 项目交付/售后

关注项目版本、设备能力判断、历史追溯和升级说明。

### 5.2 典型使用场景

1. 产品经理为新产品线定义功能集，并沉淀多个能力版本。
2. 研发人员确认某功能集在 V2.0 与 V3.0 之间的能力变化。
3. 测试人员根据某功能集版本确定当前测试范围。
4. 售前人员确认某机型在某版本下的能力范围是什么。
5. 售后人员通过操作日志与版本记录回溯某次能力变更。

## 6. 产品整体流程

### 6.1 总体业务闭环

平台整体围绕以下主线建设：

1. 需求引入
2. 能力定义
3. 功能集编排
4. 版本沉淀
5. 日志留痕
6. 能力追溯
7. 后续映射与验证

### 6.2 MVP 主流程

当前 MVP 主流程为：

1. 创建功能集
2. 填写功能集基础信息
3. 选择目标功能集进入版本记录
4. 新增版本记录
5. 保存版本内容
6. 查看版本列表与日志记录

## 8. 功能性需求

### 8.1 模块一：功能集字典

#### 8.1.1 功能集列表

需求说明：

- 平台应展示功能集列表
- 每个列表项应包含：
  - 功能集名称
  - 功能集编码
  - 功能集状态
  - 版本记录数量
  - 最新版本号

验收标准：

- 用户进入页面后可直接看到功能集列表
- 点击任一功能集列表项，右侧详情同步切换

#### 8.1.2 功能集查询

需求说明：

- 支持按功能集名称查询
- 支持按功能集编码查询
- 查询方式为输入关键词后点击“查询”或按 Enter 执行
- 点击“重置”恢复全部列表

验收标准：

- 查询关键词命中名称或编码时，应返回匹配功能集
- 查询结果应联动右侧详情区
- 查询无结果时，应显示空状态提示

#### 8.1.3 新增功能集

需求说明：

- 支持通过弹窗新增功能集
- 字段包括：
  - 功能集名称
  - 功能集编码
  - 功能集状态（默认启用）
  - 功能集说明

验收标准：

- 必填字段未填写时不可保存
- 保存成功后应出现在列表中
- 新增成功后默认选中新建的功能集

#### 8.1.4 编辑功能集

需求说明：

- 支持编辑既有功能集基础信息
- 状态通过开关形式进行启停控制

验收标准：

- 编辑后列表与详情内容同步更新
- 状态切换应即时反映在列表和详情中

#### 8.1.5 删除功能集

需求说明：

- 当前版本下若功能集已存在版本记录，则不允许直接删除
- 后续平台化阶段建议升级为“归档/废弃优先”

验收标准：

- 已关联版本的功能集点击删除时，应给出阻止提示
- 无版本的功能集可执行删除确认

### 8.2 模块二：版本记录

#### 8.2.1 版本记录列表

需求说明：

- 支持展示当前功能集下的版本列表
- 每条版本记录应包含：
  - 版本号
  - 版本名称
  - 能力范围
  - 版本描述
  - 创建时间
  - 操作

验收标准：

- 进入某功能集后可直接查看其版本列表
- 列表内容与当前选中功能集保持一致

#### 8.2.2 新增版本

需求说明：

- 支持通过弹窗新增版本
- 字段包括：
  - 版本号
  - 版本名称
  - 能力范围
  - 版本描述

验收标准：

- 必填字段未填写时不可保存
- 新增后应保存为当前功能集下的一条版本记录

#### 8.2.3 保存版本

需求说明：

- 用户填写版本号、版本名称、能力范围和版本描述后，可保存为版本记录
- 当前 MVP 暂不维护版本状态字段

验收标准：

- 保存后版本记录应保留在当前功能集的版本列表中
- 版本列表应展示该记录的创建时间

#### 8.2.4 查看与编辑版本

需求说明：

- 支持查看版本详情
- 支持编辑现有版本

验收标准：

- 点击查看时以只读态打开
- 点击编辑时可修改并再次保存

#### 8.2.5 删除版本

需求说明：

- 支持删除不再需要的版本记录
- 删除前需进行二次确认

验收标准：

- 删除成功后应从当前功能集版本列表中移除

### 8.3 模块三：操作日志

#### 8.3.1 操作日志展示

需求说明：

- 支持查看当前功能集相关的操作日志
- 每条日志应包含：
  - 操作时间
  - 操作类型
  - 操作对象
  - 操作人
  - 处理结果

验收标准：

- 用户可在“操作日志”视图中看到日志记录
- 日志内容应与当前功能集相关

### 8.4 模块四：批量导入

#### 8.4.1 导入入口

需求说明：

- 页面顶部应提供“批量导入”入口

#### 8.4.2 导入模板说明

需求说明：

- 弹窗中应展示 JSON 模板结构
- 模板字段至少包括：
  - 功能集编码
  - 功能集名称
  - 功能集状态
  - 功能集说明
  - 版本号
  - 版本名称
  - 能力范围
  - 版本描述

#### 8.4.3 导入提交

需求说明：

- 用户应能上传或拖拽导入文件并提交
- MVP 阶段允许先以原型提示形式模拟提交结果

### 8.5 模块五：字段规范

需求说明：

- 平台应展示当前 MVP 字段规范与填写口径
- 功能集与版本字段均需提供示例和约束说明

验收标准：

- 用户可在字段规范页查看所有当前已落地字段说明

### 8.6 模块六：流程与交互说明

需求说明：

- 平台应提供一页独立的“流程与交互说明”
- 该页面用于说明：
  - 当前模块定位
  - 整体流程闭环
  - 模块职责
  - 交互说明
  - 与后续规划的关系

验收标准：

- 用户可在导航中独立查看该页面
- 内容需同时服务于评审与汇报场景

## 9. 非功能性需求

### 9.1 可用性

- 页面操作路径清晰，列表、详情、版本、日志四层关系明确
- 查询、切换、弹窗关闭等交互行为一致
- 空状态、阻止提示、错误提示具备明确反馈

### 9.2 可维护性

- 前端页面结构需要支持后续扩展新模块
- 功能集、版本、日志等数据结构应保持清晰分层
- 页面说明与字段规范应可持续维护

### 9.3 一致性

- 状态标签、按钮、卡片、表格、弹窗交互风格一致
- 各页面文案口径统一

### 9.4 性能

- 在当前原型阶段，常规列表切换与查询应无明显卡顿
- 一期真实系统中，查询应在常见数据量下快速返回

### 9.5 安全与权限

- 删除、保存等关键动作需具备权限控制能力预留
- 日志数据需支持审计留痕扩展

### 9.6 兼容与响应式

- 桌面端为主要使用场景
- 页面在窄屏下应保持结构不破碎

## 11. 权限与角色协同

### 11.1 当前阶段角色协同原则

当前 MVP 可先不实现完整权限模型，但需明确角色关注点：

- 产品：负责能力定义与版本规划
- 研发：负责字段、能力与实现边界确认
- 测试：负责版本范围与验证依据确认
- 售前/销售：负责能力查询与对外口径使用
- 售后/交付：负责历史版本追溯与能力核对

### 11.2 后续权限方向

后续建议逐步支持：

- 查看权限
- 编辑权限
- 版本治理权限
- 删除/归档权限
- 审批权限
- 审计查看权限

## 12. 风险、依赖与约束

### 12.1 关键风险

1. 功能项、功能集、版本三类概念边界不清，可能导致平台内定义混乱。
2. 若无统一字段结构化建模，后续扩展到机型绑定和版本映射会出现重构成本。
3. 若删除与版本变更没有审计与引用校验，将影响追溯链路完整性。
4. 若平台只服务研发视角，将无法成为真正的跨角色能力事实源。

### 12.2 关键依赖

- 产品侧统一功能定义口径
- 研发侧统一字段编码与数据结构约束
- 测试侧明确版本验证边界
- 后续若扩展，需要机型、软件版本、项目与测试数据配合接入

### 12.3 当前约束

- 当前系统仍处于 MVP 原型阶段
- 大量平台化模块暂未真实落地
- 当前文档需要同时兼顾短期落地与长期规划，需明确分阶段边界

## 13. 分阶段路线图

### 13.1 MVP 阶段

目标：完成最小治理闭环。

范围：

- 功能集字典
- 功能集版本记录
- 操作日志
- 批量导入
- 查询与字段规范
- 流程与交互说明

### 13.2 一期阶段

目标：从页面原型升级为可治理的能力治理平台。

建议补充：

- 功能项字典
- 功能集与功能项关联
- 版本评审与状态治理
- 评审与冻结记录
- 引用校验
- 历史版本对比
- 更完整的导入导出能力

### 13.3 二期阶段

目标：建立机型能力与软件实现之间的映射关系。

建议补充：

- 机型功能集绑定
- SKU/区域/项目关联
- 软件版本映射
- 推荐版本与最低支持版本说明

### 13.4 三期阶段

目标：形成跨角色协同的完整能力治理平台。

建议补充：

- 测试与验收
- 审批与审计
- 项目定制转标准能力治理
- 多机型、多版本查询与对比

## 14. 验收标准

### 14.1 当前 MVP 验收标准

- 用户可新增、编辑、启停功能集
- 用户可查询功能集名称与编码
- 用户可新增、查看、编辑和删除版本记录
- 用户可查看版本列表与操作日志
- 用户可通过批量导入入口查看模板并提交导入
- 用户可查看字段规范与流程说明页面

### 14.2 产品层验收标准

- 平台能够清晰区分功能集定义与功能集版本
- 平台能够回答“当前功能集有哪些版本、最新版本是什么”
- 平台能够留存关键操作日志
- 平台能够为后续机型绑定、软件版本映射与测试验收预留清晰承接关系

### 14.3 文档层验收标准

- 背景、目标、范围、流程、功能需求、非功能需求完整
- 当前阶段与后续阶段边界明确
- 可同时用于需求评审与立项汇报
